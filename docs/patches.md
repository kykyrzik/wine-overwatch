# Что делает каждая правка

Смещения — файловые, для сборки `WS11WineSikarugir11.0_1` (x86_64). Точные байты — в `builds/<сборка>/patches.tsv`.
Имена методов Objective-C даны по исходникам Wine 11.0 (`dlls/winemac.drv/cocoa_app.m`, `mouse.c`); в бинарнике символов нет.

## ntdll.so

### gsbase-loop — зависание загрузчика игры
На macOS обработчик сигналов крутит `check_invalid_gsbase()` бесконечно: при сбое исполнения он «чинит» gsbase снова и снова.
Upstream исправил это в Wine 11.4 (коммит 6f6f66ee); в Sikarugir 11.0 исправления нет.
Правка: переход `je` около `0x38b9f` ведёт в пещеру `0x37ef1` с проверкой `testb $0x10,0x4(%rbx)`, которая выходит из цикла.

## winemac.so — мышь

Основная идея: в бою игра читает Raw Input и после каждого пакета ставит курсор в центр (`SetCursorPos`).
Штатный драйвер для этого физически переносит курсор macOS, и перенос портит сдвиги мыши. Правки переводят бой на «отвязанный»
курсор: пока идёт захват, физический курсор стоит, а игра получает только относительные сдвиги.

| id | где | что |
|---|---|---|
| clip-relative | `-[WineApplicationController handleMouseMove:]`, `0x8e3e` | при захвате курсора движение всегда относительное |
| warp-keeps-deltas | `setCursorPosition:`, `0x831d` | перенос курсора не стирает накопленные относительные сдвиги (маска очистки очереди событий) |
| no-forced-absolute | `handleMouseMove:`, `0x8c12` | игнорировать `forceNextMouseMoveAbsolute` — после щелчка был скачок |
| warp-dissociates | `setCursorPosition:`, `0x81d2` → пещера `0x8301` | при захвате вместо переноса — `CGAssociateMouseAndMouseCursorPosition(false)` |
| unclip-reassociates | `-[WineConfinementClipCursorHandler stopClippingCursor]`, `0xe94a` → пещера `0xe954` | при снятии захвата курсор привязывается обратно |
| getcursorpos-server | `macdrv_GetCursorPos`, `0x2e291` | `GetCursorPos` отдаёт позицию курсора Wine, а не застывшего физического |
| drop-first-after-warp | `handleMouseMove:`, `0x8bee` | первое событие после настоящего переноса отбрасывается: macOS подмешивает в его сдвиг расстояние переноса |
| buttons-no-move | таблица флагов кнопок `0x41140`, `0x2eda2`, `0x2edb3` | кнопки мыши без `MOUSEEVENTF_ABSOLUTE\|MOVE` |
| buttons-zero-xy | `macdrv_mouse_button`, `0x2edbb` | кнопки уходят с x,y = 0 |
| wheel-no-move | обработчик прокрутки, `0x2f096`…`0x2f26d` | колесо: x,y = 0, только флаг колеса |
| fullscreen-clip | `macdrv_clip_cursor`, `0x0c633` | в полноэкранном режиме захват включается, пока игра прячет курсор |

### Почему кнопкам и колесу нужны нулевые координаты
`wineserver` этой сборки собирает Raw Input мыши не как upstream: в `lLastX/lLastY` кладёт `x,y` входного события как есть,
а флаг абсолютности (`usFlags`) выводит из `MOUSEEVENTF_ABSOLUTE`. Драйвер передаёт в кнопке и колесе позицию курсора на экране.
С флагом ABSOLUTE это давало небольшой рывок камеры, без него — рывок на сотни пикселей при каждом щелчке.

### Почему полный экран решается по видимости курсора
В полноэкранном режиме игра держит `ClipCursor(весь экран)` и в бою, и в меню. Штатный драйвер прямоугольник во весь экран
игнорирует, и захват не включается никогда. Отличить бой от меню можно только по тому, что в бою игра вызывает `SetCursor(NULL)`:
правка проверяет поле `clientWantsCursorHidden` контроллера (смещение `0x122`).
